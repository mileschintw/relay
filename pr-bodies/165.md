Closes #165

## Why

#159 taught `waitchecks` to pass a PR whose changed paths no `pull_request` workflow's `paths` filter covers, and its exit-0 hint sends the coordinator to *Finishing a lane* step 4. That step merges only once `ready` lists the lane under Ready to merge, but `ready` left such a PR at `no checks reported` and `merge` refused it, so an unattended lane ended Stuck.

## What changed

- `ready` (`ready_done`): when a PR's checks come back as `no checks reported`, it asks `uncovered_line` (the same function `waitchecks` uses). When CI does not cover the PR's paths, the lane goes under Ready to merge, its line ending with `(CI does not cover these paths: ...; no checks to wait for)`. A covered PR with no checks stays at `no checks reported`; a failed lookup also leaves it there.
- `merge`: `READY_TO_MERGE` accepts that suffix, so `merge` takes the lane at the head `ready` printed.
- `ready`'s usage text describes the rule.
- `.github/workflows/test.yml`: the `test` tier also runs for `plugin/skills/setup/templates/`, which `tests/test_relay.py` reads.

## Tests

## Review

- Standards: `checks, uncovered = (...) if line else (checks, "")` reassigned the same values. Fixed: a plain `if line:`.
- Standards: the `READY_TO_MERGE` suffix ended in a greedy `.*\)`, which would also accept a trailing `(conflict check skipped: ...)`. Fixed: it now has to end with the uncovered line's own `; no checks to wait for)`.
- Standards: `ready` now re-reads the workflow files for each lane with no checks, with no sharing through `ReadyLookups`. A slow lookup falls back safely. Follow-up: Refs #169.
- Standards: no test for a failed lookup on an uncovered PR, or for a conflicting one. Left as a note, since `uncovered_line`'s failure paths are already tested through `waitchecks`.
- Spec: ci-fallbacks.md *Which case* still has no row for `ready`'s `no checks reported`. Only covered PRs reach that line now, and `waitchecks` exit 3 has its row, so this is a note and not a contradiction.
