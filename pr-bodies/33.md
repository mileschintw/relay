## Why

`ready` reports `no CI configured` when a PR has no checks and the repo has zero GitHub Actions workflows. A repo whose CI runs outside Actions (CircleCI, Buildkite, any app posting commit statuses) also has zero workflows, so its PR read `no CI configured` before the external check reported, and the coordinator offered a local-check merge too early. Setup step 9 made the same misread and offered such a repo a workflow.

## What changed

- `plugin/tools/relay.py`: `no_workflows` is now `no_ci`. With zero workflows it also looks at the default branch head (`commits/HEAD/status` and `commits/HEAD/check-runs`); a `total_count` above 0 on either, or a failed lookup, keeps `no checks reported`. A repo with workflows makes no `commits/HEAD` call. The `ready` docstring says so. The `no CI configured` / `no checks reported` wording is unchanged.
- `tests/fake_gh.py`: answers `commits/HEAD/status` and `commits/HEAD/check-runs` (`head_statuses`, `head_check_runs`, default 0), and logs every call to `$RELAY_FAKE_GH.calls`.
- `tests/test_relay.py`: `test_ci_outside_actions` (a status, a check-run, nothing, a failed `/status`, a failed `/check-runs`) and `test_workflows_skip_head_lookup`.
- `plugin/skills/setup/SKILL.md` step 9: with zero workflows, run the same two lookups; on a count above 0, say CI was found outside Actions; on a failed lookup, say so; offer a workflow only when both print 0.

Out of scope, as triaged: external CI that never reports on the default branch (PR-only) still reads `no CI configured`; the user's yes before a local-check merge stays the guard.
