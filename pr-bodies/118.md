## Summary

Profiling showed `ready` is slow only under load: 8 s idle against 146 s while builds saturate CPU and memory, past an agent's 2-minute command limit, so the whole output was lost. Rather than a faster lookup, `ready` now has a time budget and prints what it has.

```diff
 run(cmd)
+  past ready's deadline: return TIMED_OUT, start nothing
+  still running at the deadline: kill it (2 s grace for pipes), return TIMED_OUT

 cmd_ready
+  deadline = now + $RELAY_READY_SECONDS (default 75 s)
   records scan (no lookups, always runs)
-  fetch, relay.py check, Parents
+  timed_step(fetch | relay.py check | Parents)   # cut off: drop its lines, use a safe fallback
   for each lane
     print its line (from the status file)
-    sort it into sections
+    sort it; if a lookup ran past the budget: drop its findings, list it under Skipped
+  Skipped: lookups past ready's 75 s budget ($RELAY_READY_SECONDS): fetch, Parents, lanes 114, 140, 61 done lanes not in plan.md's Now table
+    hint: the machine is likely busy ... rerun `ready` once it is quieter, or in the background ...
```

`ReadyLookups.prs` no longer caches a timed-out PR list, so every lane that needs it lands under Skipped instead of `lookup failed`. A skipped Parents step holds every GO, as a failed one does.

## Evidence

Profile of `ready D:/Repos/relay-coord --checkout D:/Repos/relay` (64 lanes):

- **Before:** idle 7.9 s (14 calls, all `gh` / `git fetch`). Under load (24 CPU burners plus 3 GB of memory hogs on 12 cores): 146 s, with one `gh pr list` at 48 s and `git fetch` at 44 s.
  **After:** idle 8 s, no Skipped section. Under the same load, `ready` itself stops at about 77 s and exits 0, with every lane's line plus the Skipped line. Interpreter startup under that load sometimes added more wall time (once 177 s before `main`), which `ready` cannot bound; the hint points to a background run.

Tests (`ReadyTimeoutTests`):

```text
pr list sleeps 30 s, budget 3 s -> ready returns in < 20 s, lanes 12 and 13 printed and listed under Skipped, "No status yet" still printed, no "lookup failed"
budget 0 -> gh never called; fetch, Parents and lanes listed as skipped
step cut off midway -> its lines dropped, fallback returned (no false relay.py warning)
budget "soon" / nan / -1 / inf -> exit 2
grandchild holding the pipes -> run returns within 20 s
```

`py -3 -I tests/test_relay.py`: 160 tests OK. `claude plugin validate .`: passed.

## Review

- Round 1, blocker: a relay.py check cut off midway still printed its return value (a false "detached HEAD" warning). Fixed: `timed_step` returns a fallback when a step times out.
- Round 1: a 124-character docstring line was rewrapped. Untested behaviours (bad budget, a step cut off midway) now have tests. A NaN or inf budget is a usage error. An interrupt kills `run`'s child. Parked lanes say the Parents lookup "is skipped". The `n` snapshot was renamed to `before`. All fixed.
- Notes, left as they are:
  - On Windows `kill()` stops only the direct child, so a killed `git fetch`'s `git-remote-https` can keep running. The 2 s pipe grace stops it from holding `ready`. A ref lock it leaves makes the next fetch fail, which `ready` already handles as a failed fetch.
  - Module-level `deadline` / `timed_out` state, and the snapshot pattern in three places.
  - The interrupt kill has no test.
  - Skipped done lanes outside Now are counted, not named, on purpose.
- Round 2: no blockers.

## Merge Danger

**Door:** two-way

**Blast Radius:** `ready` only. Other commands have no deadline (`deadline` is None outside `ready`, with a test). A coordinator with more than 75 s of real lookups would see lanes under Skipped. The fix for that is `RELAY_READY_SECONDS`.
