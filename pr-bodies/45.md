Coordinators no longer hand-write the merge loop in *Finishing a lane* step 4: `relay.py merge <records> <key>...` merges lanes in the given order and stops at the first problem.

Closes #45

## What changed

- `plugin/tools/relay.py`: new `merge` subcommand (`cmd_merge`, after `cmd_waitchecks`).
  - Up front: every key must be listed under `ready`'s Ready to merge and nowhere else (the same `ready_done` check `ready` runs), and no key may be given twice. Otherwise nothing merges.
  - Per key, in order: `wait_checks` (from `waitchecks`, no second polling loop); the PR head must still be the sha `ready` printed; `mergeStateStatus` must be `CLEAN` (`UNKNOWN`, which GitHub reports while it recomputes after the previous merge, is asked again after 5, 15 and 30 s); then `gh pr merge <N> --merge --match-head-commit <sha>` and one line with the merge time.
  - The first key that fails gets one line on stderr saying which and why, exit 1, and nothing after it merges.
  - After the last merge: the default branch's push run for the merge commit (`gh run list --branch <base> --event push --commit <sha>`), or a line saying none has appeared yet, with the command to check later.
  - Docstring: usage line, `merge` section, exit codes.
- `tests/fake_gh.py`: answers for `pr view` (head, merge state, merge time), `pr merge` (with a failure option) and `run list`.
- `tests/test_relay.py`: `MergeTests`, covering:
  - two lanes merge in order with `--match-head-commit`;
  - a moved head, a failed check, a non-`CLEAN` state and an `UNKNOWN` state that never clears each stop the first key with no merge;
  - keys not under Ready to merge are refused before any merge, as are repeated keys;
  - a failed `gh pr merge` stops the rest;
  - a failed merge-time lookup still counts as merged;
  - the push run is reported, or its absence is said.
- `plugin/skills/coordinate/SKILL.md`: *Finishing a lane* step 4 runs `relay.py merge` after `waitchecks` passes, says what to do on each kind of stop, and has the coordinator read the default branch's push run instead of rerunning checks locally.
- `README.md`: Layout table row for `relay.py` lists `merge`.

## Review

- Step 4 named no action for a non-`CLEAN` state, a failed lookup or a failed `gh pr merge`: fixed. Every stop other than "not under Ready to merge" goes to the user with the line, and the coordinator reports which lanes merged.
- The pre-check accepted a status file without `time`: fixed (now required, as `ready` requires it).
- The push-run lookup failure went to stdout: fixed (stderr).
- Untested paths (`UNKNOWN` after every retry, merge-time lookup failure): tests added.
- A repeated key could fail only after an earlier merge: fixed (refused up front).
- The fake gh docstring left out fields `merge` reads: fixed.
- Notes left as they are:
  - The pre-check does not repeat `ready`'s parent-issue check; a parent never has a done lane with a PR.
  - The push run is looked up on the last PR's base branch, which is the default branch for every relay lane.
  - Exit 3 (no checks appeared) folds into exit 1. A key only gets there after `ready` has seen its checks pass.
  - All keys are checked against `ready` once, up front, rather than before each merge. The per-key head and `CLEAN` gates and `--match-head-commit` cover a merge that changes the next lane.
  - `LOOKUP_ERRORS` is new; the existing handlers still spell the same tuple out, and are left untouched to keep this diff in its lane.
