## What

CI now runs only the jobs a PR's paths need, and `relay.py waitchecks` no longer waits the CI start wait for a PR that no workflow covers.

- **`.github/workflows/test.yml`**: a new `changes` job diffs the PR's merge commit against its first parent (the base tip) and sets two outputs. `test` (both OSes) runs when `plugin/tools/`, `tests/` or `.github/workflows/` changed. `validate` runs when `plugin/`, `.claude-plugin/` or `.github/workflows/` changed. A push to `main` runs both. Skipped jobs still report a check (conclusion `skipped`, which `checks_state` and `gh pr checks` count as passed), so a docs-only PR like #158 finishes after the one short `changes` job instead of waiting ~5 minutes for the Windows job. Branch protection would see the same thing if checks ever become required.
- **`plugin/tools/relay.py`**: for repos that filter a whole workflow with `paths` or `paths-ignore` (and so report no check at all), `wait_checks` now calls `uncovered_line` on its first poll that finds no checks. When every default-branch workflow that runs on `pull_request` has a filter that none of the PR's changed paths pass, it prints `CI does not cover these paths: ...` and exits 0 with no CI start wait. In every doubtful case it falls back to today's wait: an unfiltered workflow, a changed path under `.github/workflows/`, 300 or more changed paths, no changed paths, or a failed lookup. New helpers sit beside `ci_case`: `on_block`, `pull_request_filters`, `paths_filter`, `path_pattern` (GitHub's glob rules: `*`, `**`, `**/`, `?`, `+`, `[...]`, `!`), `path_filter_matches` and `workflow_texts`. `ci_case` and `runs_on_pull_request` now use them, with unchanged behaviour. The exit-0 hint and the help text mention the new pass.
- **`plugin/skills/setup/SKILL.md`** step 9: the `changes` job is optional for repos that copy the workflow.
- **`docs/layout.md`**: the `relay.py` and `test.yml` rows.
- **Tests**: `UncoveredPathsTests` in `tests/test_relay.py`; `tests/fake_gh.py` answers `api .../pulls/<N>/files` from `pr_files`.

## Why both

The issue prefers job-level conditions that still report a check, and that is what relay's own workflow uses. The issue's `waitchecks` bullet and the lane tests also ask for the workflow-level `paths` case, which is what a repo copying the workflow with a plain `paths:` filter would hit. Without it, such a repo's docs PRs would wait the full CI start wait and then land in `ci-fallbacks.md`.
