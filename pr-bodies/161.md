## Summary

On a Windows cp950 locale, a piped `relay.py` stdout used the locale code page, so any non-ASCII character that cp950 cannot hold (`›` in records text) crashed the command with `UnicodeEncodeError` after its work was done. `py -3 -I` ignores `PYTHONIOENCODING`, so there was no workaround.

`main()` now reconfigures stdout and stderr to `encoding="utf-8", errors="replace"` before argparse runs, for every command. This replaces the older per-command `reconfigure(errors="replace")` that only `localcheck`, `waitchecks` and `merge` had.

## Changes

- `plugin/tools/relay.py`: `main()` switches stdout and stderr to UTF-8 first thing, so argparse errors are covered too. The per-command block is gone.
- `tests/test_relay.py`:
  - New `StatusTests.test_non_ascii_on_a_cp950_console` runs `relay.py status` as a `-I` subprocess with stdout and stderr wrapped as cp950. It checks exit 0, the status file is written, the UTF-8 echo holds `›` and Chinese, and an argparse error with `'完成'` on stderr. No traceback.
  - `SafeExitTests.test_non_ascii_check_name_on_a_cp1252_stdout_exits_by_the_checks` now expects UTF-8 output instead of cp1252 with `?`.

## Trade-off

A pipe reader that decodes with the console code page (a plain cp950 PowerShell pipe) now shows mojibake for Chinese text instead of crashing. Before, it got correct Chinese until the first `›` and then crashed. Git Bash pipes, Claude Code's Bash tool and its PowerShell tool (`OutputEncoding` utf-8) read the output correctly. An interactive console is unaffected, because Python writes to it through the Unicode console API either way.
