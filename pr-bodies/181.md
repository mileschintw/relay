## What

`relay.py merge` used to print the default branch's push run once, at merge time, when it was nearly always `queued`. Now, after the last merge, it waits for the push runs on that merge commit and exits non-zero when one fails. `waitchecks --push <sha>` does the same wait for any commit, so a release (`docs/releasing.md` step 2) uses it in place of `gh run list` by hand.

## How

- `wait_push_run` polls `gh run list --event push --commit <sha>` on project.md's CI start wait schedule (0, 1, 3, 6 min by default) until a run appears, then every 30 s until each run has completed. The cap is 20 CI start waits, the same as the checks watch.
- Each run gets one line: workflow, conclusion, short sha, URL. Under a `failure`, `timed_out` or `startup_failure` run, a `failed jobs:` line comes from `gh run view --json jobs`.
- `cancelled` and `skipped` decide nothing, the same rule `ready` follows since #182. Next to a success the result is a pass, next to a failure it is red, and when no other run exists it counts as no run.
- Exit codes:
  - `waitchecks --push`: 0 green, 1 red, 3 no run appeared or decided, 4 lookup failed, 5 timed out.
  - `merge`, once every key has merged: 6 red, 3 no run, 5 timed out, 4 when the merge commit or push run lookup failed (it names the `waitchecks --push` command to rerun).
  - `merge` now reads the CI start wait before it merges anything, so a bad value is a usage error (2) with nothing merged.
- Each new exit has its own hint in EXIT_HINTS. The docstring's waitchecks, merge and Exit sections describe the new behaviour.
- Docs:
  - `coordinate/SKILL.md` (*Finishing a lane* › **Merge**): on exit 6, open a follow-up issue under the standing permission, tell the user, and put it first in the next frontier.
  - `unattended.md`: says the same for unattended runs.
  - `docs/releasing.md` step 2: uses `waitchecks --push`.
  - `docs/layout.md`: its relay.py row matches the new behaviour.
- `tests/fake_gh.py`: `push_runs` (one answer per `run list --commit` call), `run_jobs` (`run view --json jobs`), and `defaultBranchRef` from `repo view`.

## Tests

`PushWaitTests` covers:
- green after queued and in progress
- red, naming the workflow, sha, failed jobs and URL (also `timed_out` and `startup_failure`)
- no run appeared
- a run still in progress past the cap; a failure already seen stays red past the cap
- cancelled or skipped runs, alone and next to a success or a failure
- lookup failures, before a run appears and during the watch
- usage errors
- `merge`'s 0, 6, 3 and 5 exits, its rerun line after a failed lookup, and a bad CI start wait stopping it before any merge
