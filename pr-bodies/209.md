## What

`relay.py merge` no longer waits out the CI start schedule for a push run that can never come. After the last merge it reads the default branch's workflow files. When none names `push` in its `on:`, it prints one line saying so (with the files it read) and exits 3, the exit it already ended on after the full wait. A repo with a push-triggered workflow waits as before. A failed workflow lookup prints one line on stderr and keeps the wait.

## How

- `plugin/tools/relay.py`:
  - `on_events`: the `on:` event reading that `pull_request_filters` held, now taking the event regexes, so `pull_request_filters` and the new `runs_on_push` share one reader (no second parser).
  - `runs_on_push`: true when a workflow's `on:` names `push`, inline or as a key or list item. A `branches`, `branches-ignore` or `tags` filter is not read, so such a workflow still waits (errs toward waiting).
  - `cmd_merge`: the check before `wait_push_run`, using `workflow_texts`. A missing `.github/workflows/` folder counts as no push workflow, since `gh run list --event push` only sees Actions runs.
  - The docstring's `merge` section and exit line, and `EXIT_HINTS["merge"][3]`, name the new case.
- `docs/layout.md`: the `merge` entry mentions the skip.
- `tests/fake_gh.py`: `workflow_files: null` answers HTTP 404 like an absent key, so a test can override the new merge default.
- `tests/test_relay.py`:
  - `MergeTests.merge` defaults to one `on: push` workflow, so the existing merge tests keep the wait path.
  - New `PushWaitTests` tests: `test_merge_skips_the_wait_when_no_workflow_runs_on_push` (pull_request and schedule only, an empty folder, a missing folder: no `--event push` lookup, the line, exit 3), `test_merge_waits_when_a_workflow_runs_on_push_or_the_lookup_fails`, and `test_runs_on_push`.
