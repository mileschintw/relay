`relay.py localcheck` ran `git fetch -q origin` and then looked up the lane's head on origin with `git ls-remote`, and neither call had a timeout. Outside `ready` there is no deadline, so a slow network or a hung SSH connection could block `localcheck` indefinitely. That is the same hang #200 fixed in `status`, and the fetch also still ran with git's credential prompts on.

Closes #211

## What changed

- New `LOCALCHECK_GIT_SECONDS` (120), next to `STATUS_LOOKUP_SECONDS`. It bounds the fetch and the lookup separately.
- The fetch runs through `run(..., timeout=LOCALCHECK_GIT_SECONDS, env=no_prompt_env())`. A timeout fails with `git fetch origin: timed out after 120 s`. Any other fetch failure (offline, say) is still not fatal, as before: the lookup that follows decides.
- The lookup calls `pushed_head(checkout, branch, LOCALCHECK_GIT_SECONDS)`. Its `RuntimeError` now fails with one line, worded as `status` does: `could not check the head on origin: git ls-remote origin <branch>: timed out after 120 s`. Before, any `ls-remote` failure ended in a traceback.
- The docstring's `localcheck` section says that both steps run with prompts off and time out after 120 s, and that a fetch which fails any other way is not fatal.
- This reuses #200's `no_prompt_env()`, `run(..., env=)` and `pushed_head(..., timeout)`. There is no second mechanism.

## Tests

- `LocalcheckTests.test_a_hung_fetch_times_out_naming_the_step`: a fake ssh (`GIT_SSH_COMMAND`) hangs past a patched 2 s timeout. `localcheck` exits 1 and names the fetch, the fake saw `GIT_TERMINAL_PROMPT=0`, the lookup never ran, and no worktree is left.
- `LocalcheckTests.test_a_hung_lookup_times_out_naming_the_step`: the fake ssh fails the fetch at once and then hangs the `ls-remote`. `localcheck` exits 1 and names the lookup, and both calls ran with prompts off.
- The fake ssh skips git's `-G` ssh-variant probe, so that each real connection is counted once.
- The existing `LocalcheckTests` still pass. That covers a normal run.

## Review

The Standards and Spec reviews against #211 and the lane brief found no blocker. One finding was fixed:
- The lookup's failure line named the branch twice (`could not look up lane-12 on origin: git ls-remote origin lane-12: ...`). It now uses `status`'s wording. This was reviewed as a second round: a message and its assertion only, no blocker.

Notes, left as they are:
- An ssh prompt (host key, passphrase) is not refused, only bounded by the 120 s timeout. This is the same choice as #200: setting `GIT_SSH_COMMAND` would override the user's ssh config. "Never wait on a prompt" holds for git's own prompts.
- Worst case, `localcheck` now waits 240 s, because the fetch and the lookup each get 120 s.
- The new test helper `hung_origin` repeats the fake-ssh setup of #200's `status` hang test. Moving it to `Base` would mean editing that test, which is outside this lane's own tests.
- When the fetch fails without timing out and the lookup succeeds, the head may be missing locally. In that case `git worktree add` fails with a less clear message. This is unchanged from before. A "warning: fetch failed" line would make it clearer.
- `default_branch()` and `git rev-parse` still run with no timeout. Both are local, with no network.
